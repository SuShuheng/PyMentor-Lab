## Integrated claim

The frozen competition claim is that a single student identity can traverse the
full closed loop with deterministic policy transitions and persisted evidence,
not UI-only or Agent-only assertions. The gate proves three integration
boundaries the owner unit tests do not cover together:

1. **Cross-table closed loop.** A single resettable identity moves through
   `EvidenceEvent` -> `LearningPath` -> `TaskInstance` -> `CodeRun` ->
   `AssessmentResult` -> `MasteryState` (+ `MasteryStateHistory`) ->
   `ReviewSchedule` (+ `ReviewAttempt`) -> `OutboxEvent`, every transition
   visible in real PostgreSQL rows.
2. **Platform-error non-penalty across the loop.** A `SANDBOX_PLATFORM_ERROR`
   during `SUBMIT` produces no `ASSESSMENT_RECORDED` evidence, leaves
   `MasteryState` and `ReviewSchedule` untouched, and still persists the run as
   `PLATFORM_ERROR` for operations — the contract invariant that the loop never
   reduces a student because of infrastructure.
3. **Admin read-side sourcing.** The admin `/api/v1/admin/students/{id}/progress`
   projection observes the same loop the student just completed, proving the
   admin surface is sourced from the same formal-state tables and not a parallel
   store.

## Two-step loop design (verified)

The loop is intentionally two HTTP commands, both idempotent:

1. `POST /api/v1/code/submissions` runs the sandbox (visible + hidden phases for
   `SUBMIT`), persists `CodeRun` + immutable `ASSESSMENT_RECORDED` evidence, and
   returns the run view with `evidence_event_id`. The task instance stays
   `ACTIVE`.
2. `POST /api/v1/tasks/{task_instance_id}/submit` consumes that evidence by
   `event_id`, calls `record_assessment_and_decide`, transitions the task to
   `COMPLETED`, and atomically commits the mastery decision + review schedule +
   outbox event in one transaction.

The integration gate exercises both steps through the real HTTP boundary so the
evidence-id handoff is verified across endpoints, not assumed.

## Red evidence (intended failures resolved during Green)

The initial focused gate surfaced real contract shapes the integration lane had
to align to without weakening any assertion:

1. `/api/v1/code/submissions` is synchronous (three-transaction orchestrator)
   and returns `200 OK` with the final run view, not a `202 Accepted` queue
   handle. The gate was corrected to assert the actual `200` + `mode=SUBMIT` +
   `passed=True` shape.
2. The code-submission endpoint records `ASSESSMENT_RECORDED` evidence but does
   **not** decide mastery; mastery is decided by the separate
   `/api/v1/tasks/{id}/submit` command that consumes that evidence by
   `event_id`. The gate now exercises both commands so the evidence-id handoff
   is verified across endpoints.
3. The task-submit mastery policy requires
   `{independence_min, transfer_min, max_hints_for_mastery, review_delay_days}`;
   the gate's task snapshot supplies a complete policy.
4. `AdminStudentProgress.mastery_counts` is a `status -> count` map, not a list
   of per-node statuses; the gate asserts the actual map shape.
5. The delayed-review rule requires the review evidence's `created_at` to be
   `>= schedule.due_at` and the `scenario_key` to match the schedule; the gate
   stamps both deterministically.

None of these were owner defects — they are the real integrated contract the
loop runs on. No owner lane was modified.

## Commands not run and reason

- **Live sandbox supervisor (Docker runtime).** The compose `sandbox` service
  is not running in this environment; the gate uses the documented
  `get_sandbox_client` FastAPI dependency seam with a deterministic adapter
  (mirroring BE-005's `FakeSandbox`). This does not bypass any formal-state
  rule: every downstream transition is asserted against real PostgreSQL tables.
  A live supervisor smoke is owned by the deployment/release gate (INT-007),
  not the deterministic learning-loop gate.
- **Playwright browser loop.** The student renderer surfaces (FE-004/FE-005)
  are verified at the API/contract boundary here; the renderer-driven loop is
  INT-007's cross-application E2E scope and depends on INT-002 unblocking.
- **Worker queue replay.** The transactional-outbox rows are asserted directly;
  cross-language Worker queue consumption is INT-004's scope.

## Remaining risk

- The deterministic sandbox adapter exercises the orchestrator and all formal
  transitions, but a live supervisor could still expose container-isolation or
  HMAC-signing faults that the seam does not surface. That risk is owned by
  INT-007's live-deployment smoke.
- The delayed-review `created_at` is stamped deterministically in-test; the
  real student-facing review surface (FE-004) is verified in INT-007.

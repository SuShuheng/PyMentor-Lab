## Integrated claim

The frozen competition claim is that Agent collaboration, progressive
resources, multimodal outputs and the streaming UI remain source-bound,
replayable, safe and usable under failure. The gate proves the integration
boundaries the BE-006/BE-007 owner unit tests cover only in isolation:

1. **Resource-job lifecycle through HTTP** with persisted progressive
   publication (PARTIAL_READY -> READY) and the dual review gate
   (FACTUAL retryable, COMPLIANCE terminal), every stage sourced from the same
   formal-state tables.
2. **Tutoring SSE relay** with the full event discriminant set
   (`content_delta`, `reasoning_delta`, `tool_call_delta`, `done`), monotonic
   order, `Last-Event-ID` cursor forwarding for reconnect/replay, and
   provider-failure degradation to a typed inline `error` then terminal `done`.
3. **Source-bound boundary**: chat completion is rejected (404) for a node
   without governed sources, and a COMPLIANCE review-gate failure never
   publishes the artifact.
4. **Provider/secret safety**: the SSE error event surfaces only stable,
   redacted fields (`code`, `trace_id`, `retryable`) — no raw upstream detail,
   provider key, or stack trace leaks through the wire.
5. **Cross-language agent-event boundary**: the Python agent-event consumer
   ingests a TypeScript-Worker-shaped `AgentAuditEnvelope` from the real Redis
   stream and persists the `AgentRun` row in PostgreSQL, proving the Worker
   emits and the API ingests against one shared contract.

## Red evidence (intended failures resolved during Green)

The focused gate surfaced real contract shapes the integration lane aligned to
without weakening any assertion:

1. `ResourceJobCreate` carries only `course_id`/`node_id`/`resource_types`;
   `source_ids` and `context_digest` are server-derived from the governed
   node's published sources. The gate's payload was corrected.
2. `SqlResourcePublicationService.stage/review/publish` take
   `(job_id, resource_type, content, mime_type, source_ids)` /
   `(resource_id, gate, passed, findings, reviewer)` /
   `(resource_id,)`; the gate was corrected to the real signatures.
3. Resource enums (`ResourceType`, `ResourceJobStatus`,
   `ResourceArtifactStatus`, `ResourceGate`) live in `app.resources`, not
   `app.models`; the gate imports from the owning module.
4. `redis.asyncio` on Windows resolves `localhost` to `::1` first and times
   out against the IPv4-only compose Redis; the gate uses `127.0.0.1`.
5. `Settings` is a frozen dataclass, not a Pydantic model; the gate uses
   `dataclasses.replace` rather than `model_copy`.

None of these were owner defects — they are the real integrated contract. No
owner lane was modified.

## Commands not run and reason

- **Live AI provider.** No provider credentials are committed; the gate uses a
  deterministic chat stream service at the documented seam and exercises the
  provider-unavailable degradation path against the real relay. A live
  provider smoke is owned by INT-007 and depends on deployment credentials.
- **MinIO object store.** The publication service is exercised through the
  in-process `ObjectStorePort` it abstracts over; the live MinIO put/digest
  smoke is owned by INT-007's deployment gate.
- **LangGraph.js Worker queue replay through BullMQ.** The BE-007 owner
  acceptance test (`workers/agent-worker/src/acceptance/workflow.integration.test.ts`)
  already covers six-role routing, RedisSaver checkpoints, and event-id
  deduplication against real Redis with the live worker container. This gate
  covers the Python-ingest side of the same contract; running the TS-side
  acceptance here would duplicate owner coverage.

## Remaining risk

- The deterministic chat stream service exercises the full relay, ordering,
  cursor, and degradation paths, but a live provider could still expose
  backpressure or partial-chunk faults the seam does not surface. That risk is
  owned by INT-007's live-provider smoke.
- The cross-language ingest test publishes one envelope shape (`RUN_STARTED`);
  the full audit-event-type matrix is covered by the BE-007 owner test on the
  TS side and the BE-006 owner test on the Python ingest side.
